---

## 1. 背景と目的

### 1.1 背景

- Typeless / Aqua Voice などの既製音声入力ツールは高品質だが、クラウド処理が前提であり、プライバシー・コスト・オフライン利用の面で制約がある。
- 2025〜2026年にかけて、ローカルで動作するASR(Qwen3-ASR、Nemotron 3.5 ASR Streaming、Apple SpeechAnalyzer 等)と小型LLM(Qwen3.5、Gemma 4 等)の品質が既製品に匹敵する水準へ到達した。
- Apple M5 Pro のユニファイドメモリと Metal / Neural Engine により、ASR + LLM の同時常駐が現実的になった。

### 1.2 目的

**完全ローカルで動作し、日本語において Typeless / Aqua Voice と同等以上の体感品質(精度 × 速度 × 整形品質)を実現する音声入力デスクトップアプリを開発する。**

### 1.3 品質の定義(既製品を超えるための3層)

既製品の品質は ASR 単体ではなく、以下の3層の合成で決まる。本アプリも同じ3層構造を採用する。

1. **ASR層**: 音声→テキストの生変換精度
2. **整形層(LLM後処理)**: フィラー除去、言い直しの解決、句読点、固有名詞表記、文体調整
3. **UX層**: ホットキー起動、リアルタイムプレビュー、カーソル位置への即時挿入

## 2. スコープ

### 2.1 ゴール(v1.0で実現すること)

- グローバルホットキーによる音声入力の開始・終了
- 発話中の低遅延ストリーミングプレビュー表示
- 発話確定後の高精度転写 + LLM整形 + アクティブアプリのカーソル位置へのテキスト挿入
- ユーザー辞書(読み→表記)による固有名詞の正確な表記
- **ASR・LLM等のエンジンを設定で差し替え可能なプラグイン型アーキテクチャ**
- 自前評価ハーネスによるエンジン構成の定量比較

### 2.2 非ゴール(v1.0では対象外)

- Windows / Linux 対応(アーキテクチャ上の将来拡張余地は残すが実装しない)
- 会議の文字起こし・話者分離(ダイアライゼーション)
- クラウドAPI連携(BYOK含む)
- 音声コマンドによるOS操作
- iOS / モバイル対応
- 翻訳機能

### 2.3 前提条件・制約

| 項目 | 内容 |
|---|---|
| 対象ハードウェア | Apple Silicon Mac(開発・検証は M5 Pro) |
| 対象OS | macOS 15.0 (Sequoia) 以降 |
| ネットワーク | 推論時は完全オフラインで動作すること(モデルの初回ダウンロードを除く) |
| 対象言語 | 日本語メイン + 日本語文中の英語混在(製品名・技術用語) |
| 開発形態 | 個人開発 |

## 3. 機能要件

### FR-1: 音声入力の起動・終了

| ID | 要件 | 優先度 |
|---|---|---|
| FR-1.1 | グローバルホットキーで録音を開始・終了できる(押下中のみ録音する Push-to-Talk と、トグル式の両方を設定で選択可能) | Must |
| FR-1.2 | メニューバー常駐アプリとして動作し、録音状態をアイコンで視覚的に示す | Must |
| FR-1.3 | 録音中は小型のフローティングHUD(波形 + プレビューテキスト)を表示する | Should |
| FR-1.4 | どのアプリがアクティブでも動作する(アクセシビリティ権限を利用) | Must |

### FR-2: 音声処理パイプライン

| ID | 要件 | 優先度 |
|---|---|---|
| FR-2.1 | VAD(音声区間検出)により発話区間を検出し、無音区間をASRに渡さない | Must |
| FR-2.2 | 発話中はストリーミングASRによる暫定テキストをHUDにリアルタイム表示する | Should |
| FR-2.3 | 発話終了確定後、バッチASRによる高精度転写を実行する | Must |
| FR-2.4 | ASR出力に対し出力検証を行う: (a) 出力言語の判定(日本語/英語以外の混入検知)、(b) 繰り返しループの検知、(c) 空出力の検知。異常時は再転写またはストリーミング結果へフォールバックする | Must |
| FR-2.5 | 検証済みテキストをLLM整形層に渡し、整形済みテキストを最終出力とする | Must |
| FR-2.6 | LLM整形が失敗・タイムアウトした場合、ASR生出力にフォールバックして挿入する | Must |

### FR-3: LLM整形層

| ID | 要件 | 優先度 |
|---|---|---|
| FR-3.1 | フィラー(「えーと」「あのー」等)の除去 | Must |
| FR-3.2 | 言い直し・自己修正(「〜じゃなくて〜」)の解決 | Must |
| FR-3.3 | 句読点・改行の付与（テキスト末尾の句点付与に加え、文脈・終助詞「〜ですね」「〜です」「〜ます」等に基づく文中の句点 `。` 自動補完を含む） | Must |
| FR-3.4 | ユーザー辞書に基づく固有名詞の表記変換(例: 「クロード」→「Claude」) | Must |
| FR-3.5 | 数値・日付等の逆テキスト正規化(ITN)(例: 「さんがつじゅうごにち」→「3月15日」) | Should |
| FR-3.6 | アクティブアプリの種別に応じた文体プロファイル切り替え(例: Slack=カジュアル、メール=敬体、エディタ=整形最小限) | Should |
| FR-3.7 | 整形の強度を「なし / 軽微(句読点のみ) / 標準 / 積極的」から選択できる | Should |

### FR-4: テキスト挿入

| ID | 要件 | 優先度 |
|---|---|---|
| FR-4.1 | アクティブアプリのカーソル位置に整形済みテキストを挿入する(ペーストボード経由 + CGEventによるキーイベント合成。アプリ互換性に応じて方式を自動選択) | Must |
| FR-4.2 | 挿入前のペーストボード内容を退避し、挿入後に復元する | Must |
| FR-4.3 | 直近の挿入結果を履歴として保持し、UIからの再コピー・修正および辞書候補の登録ができる | Must |
| FR-4.4 | 履歴増加対策として、最大保持件数(既定500件、FIFO削除)および保存期間(既定30日)による自動ローテーション・手動一括クリア機能を提供する | Must |

### FR-5: エンジン管理(差し替え可能性)★本プロジェクトの中核要件

| ID | 要件 | 優先度 |
|---|---|---|
| FR-5.1 | ストリーミングASR / バッチASR / LLM整形 / VAD の4コンポーネントは、それぞれ共通プロトコル(インターフェース)の背後に実装し、**コードの他部分を変更せずにエンジンを追加・差し替えできる** | Must |
| FR-5.2 | 使用エンジンの組み合わせは設定ファイル(または設定UI)で宣言的に切り替えられる | Must |
| FR-5.3 | モデルの重みは初回利用時に Hugging Face 等からダウンロードし、ローカルキャッシュで管理する(手動配置もサポート) | Must |
| FR-5.4 | Swiftネイティブ(MLX Swift / Core ML / Apple Speech)での全層構築を最優先とする | Must |
| FR-5.5 | エンジンごとの推論バックエンドの違いはアダプタ層で吸収する | Must |

### FR-6: ユーザー辞書・パーソナライズ

| ID | 要件 | 優先度 |
|---|---|---|
| FR-6.1 | 「読み(カナ)→ 表記」のペアを登録・編集・削除できるユーザー辞書GUIを提供する | Must |
| FR-6.2 | ユーザー辞書はLLM整形プロンプトへ動的に注入し適用する | Must |
| FR-6.3 | 辞書はプレーンテキスト(JSON/CSV)でエクスポート・インポート可能 | Must |
| FR-6.4 | 修正履歴からの辞書候補の自動提案(ユーザーが挿入直後に手で直した語を検出) | Must |

### FR-7: 評価ハーネス(開発用機能)

| ID | 要件 | 優先度 |
|---|---|---|
| FR-7.1 | 自分の音声による評価データセット(音声 + 正解テキストのペア、50〜100発話)を管理できる | Must |
| FR-7.2 | 任意のエンジン構成に対し、CER / 固有名詞F1(形態素解析ベース) / エンドツーエンドレイテンシを自動計測しレポート出力する | Must |
| FR-7.3 | 構成間の比較レポート(どの構成がどの指標で優位か)を生成する | Should |
| FR-7.4 | LLM整形プロンプトの変更前後で同一データセットに対する回帰テストができる | Should |

## 4. 非機能要件

### NFR-1: 性能(レイテンシ予算)

エンドツーエンド目標: **発話終了 → テキスト挿入完了まで 1.5秒以内(標準構成・15秒発話時)、理想 1.0秒以内。**

| ステージ | 予算(目標) | 備考 |
|---|---|---|
| VAD発話終了判定 | ≤ 300ms | 終了判定の待ち時間(サイレンス閾値)含む |
| バッチASR転写 | ≤ 500ms | 15秒発話、RTF ≤ 0.03 相当 |
| 出力検証 | ≤ 50ms | ルールベース処理 |
| LLM整形 | ≤ 500ms | 入力≒出力の短文タスク。プロンプトキャッシュ活用 |
| テキスト挿入 | ≤ 100ms | |
| ストリーミングプレビュー表示遅延 | ≤ 500ms | 発話にプレビューが追従する体感 |
| ホットキー押下 → 録音開始 | ≤ 100ms | モデルは常駐済みであること |

### NFR-2: リソース

| 項目 | 要件 |
|---|---|
| 常駐メモリ | 標準構成で合計 8GB 以下(ASR約2GB + ストリーミング約1GB + LLM約3〜5GB)。軽量構成(4GB以下)も選択可能にする |
| アイドル時CPU/GPU | 録音していない間の消費はほぼゼロ(VAD含め録音時のみ稼働) |
| アプリ起動 | モデルのウォームアップ(事前コンパイル・ダミー推論)により初回転写のスパイクを排除する |
| バッテリー | 可能なコンポーネントは Neural Engine / 量子化を優先し電力効率を確保する |

### NFR-3: プライバシー・セキュリティ

- 音声・転写テキスト・辞書・履歴は端末外に送信しない。推論時のネットワーク通信はゼロ。
- 音声データは転写完了後、既定で即時破棄する(評価ハーネス用の保存はユーザーの明示的操作のみ)。
- ネットワークアクセスはモデルダウンロード時のみ発生し、その旨をUIに明示する。

### NFR-4: 精度目標(評価ハーネスで計測)

| 指標 | 目標 |
|---|---|
| CER(自前評価セット、整形後) | 既製品(Typeless等)の同一音声に対する出力と同等以下 |
| 固有名詞F1(ユーザー辞書登録語) | ≥ 95% |
| ハルシネーション(繰り返し・言語混在・空出力)発生率 | < 1%(検証層通過後) |

### NFR-5: 保守性・拡張性

- エンジン追加が1ファイル(アダプタ実装)+設定追記で完結すること。
- 依存パッケージ・モデルのバージョンを構成ファイルで固定できること(再現性)。
- 将来のクロスプラットフォーム化を阻害しないよう、パイプラインのコアロジックとmacOS固有層(ホットキー、挿入、UI)を分離する。

## 5. アーキテクチャ方針

### 5.1 全体構成

```
┌─────────────────────────── macOS固有層 ───────────────────────────┐
│  メニューバーUI / HUD / グローバルホットキー / アクセシビリティ挿入   │
└──────────────────────────────┬────────────────────────────────────┘
                               │
┌────────────────────── パイプラインコア(OS非依存) ─────────────────┐
│                                                                     │
│  AudioCapture → [VADEngine] ─┬→ [StreamingASREngine] → プレビュー   │
│                              └→ 発話確定 → [BatchASREngine]         │
│                                     → OutputValidator                │
│                                     → [RefinerEngine(LLM)]          │
│                                     → 最終テキスト                   │
│                                                                     │
│  ※ [ ] はプロトコル境界 = 差し替え可能なエンジンスロット             │
└─────────────────────────────────────────────────────────────────────┘
                               │
┌────────────────────────── エンジン層 ──────────────────────────────┐
│  各スロットに対する複数実装(アダプタ)。設定ファイルで選択・組替え     │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.2 エンジンスロットのプロトコル定義(概念)

| スロット | 入力 | 出力 | 主な責務 |
|---|---|---|---|
| `VADEngine` | 音声フレーム | 発話開始/終了イベント | 発話区間検出 |
| `StreamingASREngine` | 音声チャンク(ストリーム) | 暫定テキスト(逐次) | プレビュー用低遅延転写 |
| `BatchASREngine` | 発話音声(完結した区間) | 確定テキスト + メタ情報 | 高精度転写 |
| `RefinerEngine` | 生テキスト + コンテキスト(辞書・アプリ種別・整形強度) | 整形済みテキスト | 整形・表記変換 |

各プロトコルには `load() / unload() / warmup()` とリソース申告(推定メモリ)を含め、エンジンマネージャがロード状態とメモリを一元管理する。

### 5.3 実装スタック

| 層 | 技術 | 理由 |
|---|---|---|
| アプリ本体 | Swift / SwiftUI + AppKit(メニューバー常駐) | 最軽量・最速。Apple純正API(SpeechAnalyzer、Foundation Models)とMLX Swiftへ直接アクセス可能 |
| 音声キャプチャ | AVAudioEngine | 標準 |
| テキスト挿入 | CGEvent + NSPasteboard + Accessibility API | 既存OSS(VoiceInk等)で実証済みの方式 |
| ML推論 | MLX(Swift/Python) / Core ML / Apple純正API をアダプタで併用 | エンジンごとに最適なバックエンドを選択 |
| 参考実装 | VoiceInk(GPL v3)、Handy(MIT)、speech-swift(soniqo) | パイプライン・エンジン実装の参照。ライセンス上コード流用の可否は個別確認 |

> 補足: 開発初期はエンジン部分をPythonプロセス(JSON-RPC/HTTPブリッジ)で動かし、確定後にSwiftネイティブへ置き換える2段階戦略を許容する(プロトコル境界が同じなら差し替え可能)。

### 6.5 実験枠(v1.0後の検証テーマ)

- **End-to-end音声LLM構成**: Gemma 4 E2B/E4B の音声入力で「音声→整形済みテキスト」を1モデルで実行(ASR+整形の統合)。

- **投機的デコーディング**: Qwen3-ASR 0.6Bドラフト→1.7Bターゲットによる転写高速化。

## 7. リスクと対応方針

| リスク | 影響 | 対応 |
|---|---|---|
| Nemotron 3.5 の日本語ストリーミング精度が不十分(新モデルで実測データ僅少) | プレビュー品質低下 | フェーズ1で最優先実測。不合格なら SpeechAnalyzer をプレビューに昇格 |
| Qwen3-ASR-1.7B-JA の品質がオリジナル比で自ドメインに合わない | 確定転写精度 | ハーネスでオリジナル/JA版をA/B。必要なら自前ファインチューニング(§6.5) |
| LLM整形による意味の改変・過剰書き換え | 信頼性 | 整形強度設定(FR-3.7)+ 生出力フォールバック(FR-2.6)+ 回帰テスト(FR-7.4) |
| 多言語ASRの言語混在・繰り返しハルシネーション | 出力破綻 | 出力検証層(FR-2.4)を必須要件として実装 |
| アプリごとのテキスト挿入互換性(Electron系・セキュアフィールド等) | UX | ペースト方式とキーイベント方式の自動切替 + アプリ別上書き設定 |

## 10. テスト戦略・品質保証

### 10.1 テストカバレッジ目標

- **目標**: テストカバレッジ **100%** を達成
- **対象モジュール**: 全ビジネスロジックおよびコア機能
  - `OutputValidator`: 言語判定・ループ検知・空文字判定
  - `RuleBasedRefinerEngine`: 4 段階整形強度（none/light/standard/aggressive）
  - `UserDictionaryManager`: JSON/CSV エクスポート・インポート
  - `VoiceInputPipeline`: コアパイプライン・エラーハンドリング
  - `AppConfig` / `EngineFactory`: 設定ファイル機構・エンジン選択
  - その他プロトコル実装

### 10.3 カバレッジ達成方針

- **ユニットテスト**: 各モジュールの入出力・境界条件を網羅
- **統合テスト**: パイプライン全体の E2E 動作を検証
- **エラーハンドリング**: 例外系・フォールバック機構を明示的にテスト
- **モック・スタブ**: VAD / ASR エンジンを Mock で置換し、外部依存を排除

### 10.4 保守性との両立

- テストは常にプロダクションコードと同期を保つ
- 新規要件追加時は、必ず対応テストを同時に実装
- コードレビューで「テストなし」のマージを拒否

## 付録A: 用語

| 用語 | 意味 |
|---|---|
| ASR | 自動音声認識(Automatic Speech Recognition) |
| VAD | 音声区間検出(Voice Activity Detection) |
| CER | 文字誤り率(Character Error Rate)。日本語ASR評価の標準指標 |
| 固有名詞F1 | 形態素解析(Sudachi等)で抽出した名詞・固有名詞の一致度。表記の正しさを測る |
| RTF | Real-Time Factor。処理時間 ÷ 音声長。小さいほど高速(RTF 0.03 = 15秒音声を0.45秒で処理) |
| ITN | 逆テキスト正規化(Inverse Text Normalization)。「さんがつ」→「3月」等 |
| EOU | End of Utterance(発話終了) |
| MLX | Apple Silicon向けML推論フレームワーク |
